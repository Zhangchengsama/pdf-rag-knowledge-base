# 按实际读取页数重建知识库

## 只读状态与问答回调

```python
from rag_service import get_knowledge_base_status, answer_question

# 只读 PDF 页数、两份建库记录和缓存文件状态，不创建文件，也不加载模型。
state = get_knowledge_base_status(road, index_path, max_pages=30)
print(state["status"], state["actual_pages"])

# 旧的 answer_question 调用和 {answer, sources} 返回格式继续保留。
# 可选回调额外收到 rebuilt、actual_pages、chunk_count、cache_signature。
updates = []
result = answer_question(road, index_path, "用户问题", model,
                         max_pages=30, on_build_status=updates.append)
```

只读状态包括 `not_built`（尚未建库）、`ready`（符合当前复用条件）、`rebuild_required`（需要重建）、`incomplete`（上次建库未完成）和 `unavailable`（源文件或记录无法读取）。`actual_pages` 是当前配置对应的有效页数；`ready` 仍沿用原有双记录及四种缓存检查，不增加内容哈希校验。回调在建库成功并加载文本之后、检索和大模型调用之前执行；回调应轻量且不抛出异常。

文本块数仅由本次问答加载的列表统计，不写入旧建库记录，也不修改其匹配规则。前端依据缓存文件路径、修改时间和大小识别旧统计，缓存变化后显示“未统计”。

## 使用方式

`app.py`、`main.py`、`eval.py` 中均有以下配置：

```python
max_pages = 11         # 读取前 11 页；设为 None 读取全文
force_rebuild = False  # 同页数内容变化时，手动设为 True
```

`force_rebuild=True` 每次调用都会重建，用完应改回 `False`。三个入口应按自己的读取需求配置；交替使用不同实际页数时会触发重建。

也可在已经加载模型的程序中直接调用：

```python
from rag_service import building_data, answer_question

# 只建库，不调用大模型 API，不需要 DEEPSEEK_API_KEY。
state = building_data(road, index_path, model, max_pages=30)
print(state)  # 例如：{"rebuilt": True, "actual_pages": 30}

# 页数相同但内容、嵌入模型或切块设置改变时强制刷新。
building_data(road, index_path, model, max_pages=30, force_rebuild=True)

# 问答入口也支持同样的设置，回答和来源的返回结构保持不变。
result = answer_question(road, index_path, "用户问题", model, max_pages=30)
```

## 判断规则

实际读取页数取 PDF 总页数和 `max_pages` 的较小值；`None` 表示全部页数。页数参数必须为正整数或 `None`。页数由 PDF 本身计算，空白页也计数，不从文本块最大页码推断。

例如：

| 场景 | 处理 |
| --- | --- |
| 100 页 PDF，从前 11 页改为前 30 页 | 重建 |
| 100 页 PDF，从前 30 页改为前 11 页 | 重建 |
| 25 页 PDF，读取上限从 30 改为 50 | 实际均为 25 页，复用 |
| PDF 总页数增加，但读取上限仍为 11，实际仍读 11 页 | 复用 |
| 实际页数相同，仅修改正文 | 默认复用，需要手动强制重建 |
| 旧缓存没有建库记录、记录损坏或四种缓存缺失任一项 | 重建 |

切换 PDF 路径或索引路径也会重新校验配对，避免把另一份文档的索引用于当前原文。

## 文件与失败处理

原有格式不变：PDF 同目录保存 `.json` 原文、`.npy` 向量和 `.pkl` BM25；HNSW 使用指定的 `index_path`。重建时四种文件一起刷新，并只编码一次。

新增两个很小的建库记录：PDF 同名 `.build.json`，以及索引文件名后追加的 `.meta.json`（例如 `test_index.bin.meta.json`）。两处记录用于核对原文缓存与独立索引属于同一次配置，避免共用路径造成错配。旧缓存第一次使用新逻辑时会重建。

覆盖缓存前先将记录置为 `building`；四种文件全部写入完成后才标为 `ready`。中断或失败会让下次调用重新建库，不会继续把半成品当成成功缓存。当前直接覆盖缓存，不保留上一版供失败时回退，也不支持多个进程同时写同一组缓存。

如果所选页没有可提取文本，或分词后没有有效词语，会提示错误，不发布成功记录。扫描版 PDF 仍需要事先 OCR。
